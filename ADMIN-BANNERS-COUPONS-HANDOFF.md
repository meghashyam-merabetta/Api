# Admin banners and coupons frontend handoff

All routes are under `/api`, require the existing admin authentication, and return `{ data }`.
List routes also return `{ pagination: { total, limit, offset, hasMore } }`. Dates are ISO 8601
timestamps with an explicit timezone offset. Validation errors use the API's existing 422 format.

## Banners

The database primary key is `banner_key`; use it in URLs. `banner_id` is generated by the backend
and is read-only. The complete record returned by admin endpoints includes all database fields.

- `GET /api/admin/banners?limit=20&offset=0`
- Filters: `status=DRAFT|ACTIVE|INACTIVE`, `is_published=true|false`,
  `is_active=true|false`, `page_name`, `search`
- Sorting: `sort_by=banner_id|display_order|created_at|updated_at`, `sort_order=asc|desc`
- `GET /api/admin/banners/:bannerKey`
- `POST /api/admin/banners` is the legacy single-record create endpoint; do not use it in the CMS Add form
- `POST /api/admin/banners/batch` creates and uploads multiple banners for one placement
- `PATCH /api/admin/banners/:bannerKey` updates provided fields
- `DELETE /api/admin/banners/:bannerKey` deletes the row and queues managed images for cleanup

Multiple banners are allowed for the same placement. The normal CMS Add Banner form must use the
batch endpoint, even when only one file is selected. Send the base placement key every time. The
backend allocates stored keys atomically:

```text
home-essentials
home-essentials-02
home-essentials-03
```

Never calculate suffixes in the frontend. Concurrent creates are serialized by the backend. The
batch response contains an array of complete created banners. Use each returned `banner_key` for
later edit and delete URLs. The placement dropdown must remain selectable when that placement
already has banners.

### Minimal Add Banner form

Show exactly four controls:

1. Banner placement — required dropdown
2. Banner name — required admin/accessibility label
3. Banner images — required multiple-file picker
4. Active — checkbox

Remove Description, CTA text, Link URL, Status, Display order, Publish start, Publish end, and
Published from this form. Do not add mobile-image, width, height, page-name, banner-type, or key
inputs. Page name comes from placement; dimensions are read from each selected image; type and
status are assigned by the backend.

Batch request:

```text
POST /api/admin/banners/batch
Content-Type: multipart/form-data
file field: uploadimage (1 to 10 JPEG/PNG/WebP files)
text field: metadata (JSON string)
maximum per file: 5 MB
maximum combined files: 10 MB
```

Example `metadata` value (JSON-stringify before appending to FormData):

```json
{
  "banner_key": "home-essentials",
  "page_name": "Home",
  "banner_name": "Everyday essentials campaign",
  "is_active": true,
  "images": [
    { "width_px": 1200, "height_px": 400 },
    { "width_px": 1200, "height_px": 400 }
  ]
}
```

`images` must be in the same order as the appended files. Read each file's natural width and height
in the browser; these are metadata only and must not be visible form fields. Do not manually set the
multipart Content-Type header because the browser must add the boundary.

For Edit only, `POST` or `PUT /api/admin/banners/:bannerKey/image` replaces that row's primary image
using one `uploadimage` file. The Add form must use `/batch` and must not expose or call the unused
mobile-image operations.

The batch endpoint uploads to S3 and creates all rows in one request. Do not call the single-banner
POST followed by separate image uploads from the Add Banner form. The single-image endpoint remains
only for replacing an existing banner's image during Edit.

Important app behavior: the existing `GET /api/app/banners` endpoint returns `image_path` and does
not return `mobile_image_path`. Phone-app integration must therefore render `image_path`; it must
not use `mobile_image_path`. The endpoint also does not apply `status`, `is_published`, or
publication-window filters. It returns `is_active`, so app UI must continue respecting that flag.
No app file was changed in this work.

The current phone app uses exact key lookup (`home-family`, `home-essentials`, `home-labs`, etc.).
Therefore, the base banner is used by the current app, while suffixed banners are admin-manageable
but are not displayed by that phone build. Supporting a carousel of multiple banners per placement
requires a separate phone-app change to select the base key plus `-NN` variants. Do not tell admins
that all suffixed banners are live in the phone app until that integration is released.

## Coupons

- `GET /api/admin/coupons?limit=20&offset=0`
- Filters: `scope=labs|products|both`, `active=true|false`,
  `state=scheduled|current|expired`, `search`
- `GET /api/admin/coupons/:code`
- `POST /api/admin/coupons`
- `PATCH /api/admin/coupons/:code` (coupon code is immutable)
- `DELETE /api/admin/coupons/:code`

Create requires `code`, `scope`, `percent`, and `max_discount_paise`. Optional fields are `active`,
`starts_at`, and nullable `ends_at`. Codes are normalized to uppercase and allow letters, digits,
underscore, and hyphen. `percent` is greater than 0 and at most 100 with two decimal places.
`max_discount_paise` is a positive integer: `10000` means INR 100. The end must be later than start.

App checkout behavior was verified: a coupon is usable only when `active=true`, its scope matches
the checkout (or is `both`), `starts_at <= now`, and `ends_at` is null or in the future. The public
coupon endpoint is `GET /api/app/coupons?scope=labs|products` and returns only currently usable
coupons. Deactivating or expiring an offer immediately removes it from app validation/listing.
